Drei Wege zum kürzesten Weg im Straßennetz: einfache Suche, Dijkstra und Floyd–Warshall – mit metrischen oder winkelbasierten Kosten, gemessener Rechenzeit und wachsender Suchfront.

Gesucht wird im Segmentgraphen des Netzes: Knoten sind die Straßensegmente, jedes mit zwei Fahrtrichtungen; ein Weg fährt ein Segment von einem Ende zum anderen und biegt am Knoten in ein anderes ab (Wenden auf demselben Segment gibt es nicht). Ursprung und Ziel sind Punkte, es zählt das nächste Segment. Die Kosten eines Übergangs mischen Länge und Richtungsänderung wie „2. BuildGraph“ von 2020 (Längenkoeffizient · (li + lj) / 2 / lmax + Winkelkoeffizient · Winkel / 180°, lmax = längstes Segment; die Auswahl „Definition“ schaltet auf die heutige DeCodingSpaces-Toolbox um: echte Meter und Winkel / 90°); voreingestellt ist wie im Original der winkelbasierte Weg (Längenkoeffizient 0, Winkelkoeffizient 1) – der Weg mit den wenigsten Richtungswechseln, nicht der kürzeste in Metern.

Die drei Verfahren der Grasshopper-Datei: 1. Shortest Path Simple sucht wie Dijkstra, findet den nächsten Knoten aber durch Durchsehen aller Knoten – einfach, aber langsam. 2. Shortest Path Dijkstra nimmt den nächsten Knoten aus einer Vorrangwarteschlange und hört am Ziel auf – schnell für wenige Wege. 3. Floyd Warshal rechnet vorab die Wege zwischen allen Paaren (n Runden über n² Paare) – langsam in der Vorbereitung, danach ist jeder Weg sofort ablesbar. Alle drei finden denselben Weg. „Betweenness rechnen“ (Run Calculation) färbt das Netz nach der Zahl der kürzesten Wege durch jedes Segment.

Probieren: Ursprung und Ziel herumziehen und auf die Rechenzeit achten; bei Floyd–Warshall dauert nur das erste Ziehen. „Suchen“ und Start zeigen, wie die Suchfront wächst: Dijkstra breitet sich vom Ursprung aus, bis das Ziel fest ist; Floyd–Warshall braucht immer alle Runden. Auf „metrisch“ umschalten und vergleichen, wie sich der Weg ändert.

Die App setzt das Modul „Street Network Shortest Path“ aus dem Parametric Planning Catalogue (DeCodingSpaces, InfAR, Bauhaus-Universität Weimar, 2020, MIT-Lizenz) neu im Browser um. Was geändert wurde, steht in QUELLE.md.

The search runs on the segment graph of the network: nodes are the street segments, each with two travel directions; a path runs along a segment from one end to the other and turns into another one at the junction (no U-turns on the same segment). Origin and destination are points; the closest segment counts. The cost of a transition mixes length and change of direction as the 2020 “2. BuildGraph” did (length coefficient · (li + lj) / 2 / lmax + angular coefficient · angle / 180°, lmax = longest segment; the “Definition” option switches to today’s DeCodingSpaces toolbox: real metres and angle / 90°); as in the original the default is the angular path (length coefficient 0, angular coefficient 1) – the path with the fewest turns, not the shortest in metres.

The three methods of the Grasshopper file: 1. Shortest Path Simple searches like Dijkstra but finds the next node by scanning all nodes – simple but slow. 2. Shortest Path Dijkstra takes the next node from a priority queue and stops at the destination – fast for few paths. 3. Floyd Warshal computes the paths between all pairs in advance (n rounds over n² pairs) – slow in preparation, then every path can be read at once. All three find the same path. “Compute betweenness” (Run Calculation) colours the network by the number of shortest paths through each segment.

Try: drag origin and destination around and watch the computing time; with Floyd–Warshall only the first drag takes long. “Search” and Start show the search front growing: Dijkstra spreads from the origin until the destination is settled; Floyd–Warshall always needs all rounds. Switch to “metric” and compare how the path changes.

The app re-implements the module “Street Network Shortest Path” of the Parametric Planning Catalogue (DeCodingSpaces, InfAR, Bauhaus-Universität Weimar, 2020, MIT license) in the browser. Changes are listed in QUELLE.md.
